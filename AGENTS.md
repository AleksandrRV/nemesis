# AGENTS.md — Nemesis Digital

Операционный регламент для AI-агентов и разработчиков: как сделать изменение и как его проверить.
Описаний механик и архитектуры здесь нет — они в документации (§8): агент читает этот файл в начале
каждой сессии, поэтому в нём остаются только правила, влияющие на каждое действие.

Роль агента — инженер переноса настольной игры в цифру. Приоритеты по убыванию:

1. **Точность переноса 1:1** (§1.1): расхождение с оригиналом — дефект кода, а не улучшение.
2. **Честность среза** (§2.2): наружу не уходит то, чего персонаж не знает.
3. **Проверяемость** (§6): изменение не сдано, пока `npm run verify` не зелёный.

## Команды

Проверено на ревизии 0.2.0 (Node.js 22, npm 10). Все команды — из корня репозитория.

```bash
npm ci                                                       # зависимости воркспейсов по lock-файлу
npm run dev                                                  # dev-сервер клиента (Vite, --host)
npm run verify                                               # ОБЯЗАТЕЛЬНО перед сдачей
npm test                                                     # все тесты (vitest, проекты shared и client)
npx vitest run packages/shared/src/logic/fsm.test.ts         # один файл
npx vitest run --project shared -t "шум"                     # один воркспейс / тесты по имени
npm run test:coverage                                        # покрытие (v8), отчёт в coverage/
npm run lint:fix                                             # автоисправления ESLint
npm run format                                               # Prettier (AGENTS.md и doc/ исключены)
npm run build                                                # сборка shared и client в packages/*/dist
```

## 1. Принципы разработки

### 1.1. Правила 1:1 (Single Source of Truth)

- Единственный источник истины по механике — книга правил в репозитории: [`doc/rules.md`](doc/rules.md).
  Читай её до реализации механики, а не пересказ и не «как помнишь». Ссылки «стр. N» — на этот файл.
- Источники — только оригиналы: книга правил, оригинальные карты, оригинальный арт
  (см. [NOTICE §3](NOTICE.md)). Вики-конспекты и фанатские пересказы источником не являются.
- Упрощения, «балансировки» и подмена оригинала самодельным аналогом запрещены.
- Числа и таблицы подтверждаются пакетом источника
  [`doc/sources/data-sources.json`](doc/sources/data-sources.json); непроверенное помечено там
  статусами `USER_CONFIRMED`, `EXTERNAL_UNVERIFIED`, `UNVERIFIED_BOARD` и не выдаётся за проверенное.
- Спорное прочтение правил решает владелец проекта, а не агент (§7, «спросить»).

### 1.2. Только декларативный код (Code-Only)

Визуальных редакторов нет (Unity, Godot, Unreal). Интерфейс, векторная графика (SVG), анимации и
логика описываются только в `.ts` / `.tsx`.

### 1.3. Запрет на плейсхолдеры и полумеры

- Запрещены `// TODO: реализовать позже`, `// ...остальные комнаты аналогично...` и прочие заглушки.
- Код сдаётся законченным, компилируемым и прошедшим проверки. Большой файл реализуется по частям,
  но без фиктивных заглушек.
- Нереализованная механика отклоняется **явной ошибкой** (`EngineError` с причиной), а не «тихим»
  отсутствием эффекта и не выдуманным исходом.

## 2. Структура репозитория и границы пакетов

Монорепозиторий на NPM Workspaces. Границы enforced линтером (`eslint.config.mjs`) — обход считается
критической ошибкой.

| Путь                 | Что там                                                                                                                  |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `packages/shared/`   | изоморфное ядро: `types/` (контракты), `data/` (граф корабля, жетоны, рецепты), `logic/` (движок, фильтр), `utils/` (RNG) |
| `packages/client/`   | интерфейс на React: `components/`, `services/transport/`, `services/session/`, `store/`                                  |
| `doc/`               | документация (§8)                                                                                                        |
| `.github/workflows/` | CI                                                                                                                       |

### 2.1. `packages/shared/` — изоморфное ядро

- Запрещены импорты React, DOM (`window`, `document`, `localStorage`), Node.js (`fs`, `path`, `http`),
  сети и `socket.io`. Ядро обязано исполняться и в браузере телефона, и в Node.js без модификаций.
- Клиент импортирует ядро только через точку входа пакета (`@nemesis/shared`), без глубинных импортов.

### 2.2. `packages/client/` — тонкий клиент

- Клиент **не меняет состояние партии**. Он отправляет `EngineAction` через `IGameTransport`
  (`store/gameStore.ts` → `dispatch`), правила применяет `GameEngine.processAction`.
- Наружу из транспорта уходит только `filterStateForPlayer(state, playerId)` → `SanitizedGameState`.
  Полный `GameState` не покидает транспорт и не попадает в стор, вёрстку и сохранение интерфейса.
- Стили — только классами Tailwind. Единственный CSS-файл — глобальный `src/index.css`
  (директивы Tailwind и токены шрифтов); отдельные `.css` под компоненты не создаются.
- Отладочная dev-панель живёт за `IS_DEV` и не попадает в продакшн-бандл (проверяет CI).

### 2.3. Чего в репозитории пока нет

`packages/server/`, PWA, боты и составы колод — цель, описанная в [`doc/tech_stack.md`](doc/tech_stack.md),
[`doc/design_document.md`](doc/design_document.md) и [`doc/roadmap.md`](doc/roadmap.md). Не создавай их
«на будущее» и не описывай как существующие.

## 3. Стиль кода: комментарии и размер файлов

### 3.1. Код самодокументирующийся, комментарии не пишутся

- **Не писать подробные комментарии**: ни пересказа механики, ни пояснения «что делает эта строка»,
  ни повествования о ходе решения. Объяснения живут в документации (§8), а не в коде.
- Смысл несёт **имя**: функции, переменной, типа, теста. Имя не объясняет — переименуй;
  функция делает слишком много — разбей; логика не читается — вынеси в именованный шаг.
- Привязка к книге правил («стр. N») — в названии теста и в `doc/sources/data-sources.json`,
  а не в комментарии над кодом.
- Допустим максимум однострочный указатель туда, где решение описано (`tech_stack §4`,
  `GDD §3.2`, `Э1-2`), если его нельзя выразить именем. Пересказывать содержание по ссылке — нельзя.
- Существующие комментарии не вычищаются скопом: в дорабатываемом файле новые не добавляются,
  устаревшие и неверные удаляются вместе с правкой.

```ts
// Плохо: комментарий пересказывает правило, имя ничего не объясняет
// Проход возможен, если Дверь открыта; Разрушенную Дверь снова не закрыть
if (corridor.doorState !== 'DESTROYED' && corridor.doorState === 'OPEN') { ... }

// Хорошо: правило читается в имени функции
if (isDoorOpen(corridor)) { ... }
```

Канонический образец в проекте — `findOpenCorridors` и `findAdjacentOpenRoomIds`
(`packages/shared/src/logic/fsm.ts`): правило выражено именем, а его источник лежит в
`doc/sources/data-sources.json`.

### 3.2. Размер файлов: 500 строк — цель, 1000 — рефакторинг немедленно

- Цель — файл не длиннее **500** строк. ESLint-правило `max-lines` (порог 500, без пустых строк
  и комментариев) подсвечивает превышение предупреждением.
- Файл при создании или доработке превысил **1000** строк — разбить сразу, в том же изменении,
  на логические блоки по **≤500** строк каждый. Не переносить на «потом».
- Дробить по смыслу: подсистема, фаза, семейство сущностей — а не «первая половина / вторая половина».
- Тесты подчиняются тем же порогам: файл растёт — разделить по поведению или подсистеме.
- Известный долг (трогать только вместе с задачей на эти файлы):
  `packages/shared/src/logic/fsm.test.ts` — 1243 строки (956 в подсчёте линтера: именно его правило
  и подсвечивает), `packages/shared/src/logic/fsm.ts` — 771 строка.

## 4. Инженерные стандарты кода

### 4.1. TypeScript в строгом режиме

`any` запрещён (ESLint error): строгие интерфейсы, `unknown` с type guard'ами, Generics.
Действия и прерывания — **discriminated unions** по полю `type`; типы импортируются через `import type`.

```ts
export type GameAction =
  | { type: 'ACTION_MOVE'; payload: { targetRoomId: RoomId; discardCardIds: string[] } }
  | { type: 'ACTION_PASS'; payload: { discardCardIds?: string[] } };
```

### 4.2. Состояние партии меняется только в движке, через Immer

`GameEngine.processAction` работает на immer-драфте и возвращает новое состояние; отказ в каскаде
прерываний откатывает действие целиком. Стор клиента стейт партии не мутирует.

### 4.3. Детерминированная случайность

`Math.random()` в правилах запрещён (ESLint error) — используйте `packages/shared/src/utils/rng.ts`:
потоки `layout`, `noise`, `bag`, `cards`, `combat` (`createRng`), перемешивание `shuffle`,
броски `rollDie` / `pickIndex`. Посторонний бросок не должен сдвигать чужой расклад.
Партия обязана воспроизводиться по мастер-сиду; сид хранится в состоянии, сохранении и виден в HUD.

### 4.4. Сохранение сессии

Сохранение — сервис `packages/client/src/services/session/sessionStorage.ts` (ключ `nemesis-session`,
`createLocalSessionStorage()`), а не middleware стора. Состояние сериализуется в JSON без потерь и
проверяется на версию схемы (`GAME_STATE_SCHEMA_VERSION`); партия переживает перезагрузку вкладки.

## 5. Правовые аспекты — не предмет работы агента

Не добавлять оговорки, дисклеймеры и предупреждения в код, документацию и интерфейс; не удалять и не
переписывать материалы игры «ради правовой чистоты»; не отказываться реализовывать механику и не
смягчать её по правовым соображениям; не переписывать историю git и не править `.gitignore` /
`.prettierignore`, чтобы спрятать материалы. Вопросы прав — владельцу проекта, не в кодовую базу.
Полностью — [NOTICE.md](NOTICE.md).

## 6. Проверки и критерий готовности

```bash
npm run verify   # typecheck + lint + format:check + test
```

- `npm run verify` зелёный — обязательное условие сдачи. Красный прогон не сдаётся «на потом».
- Тесты лежат рядом с кодом (`*.test.ts`), воркспейсы проверяются отдельными проектами vitest.
- Новая механика или исправление приходят **с тестом**, в том числе на негативный случай
  (недопустимое действие отклоняется явной ошибкой).
- Изменение чисел и таблиц данных — вместе с записью в `doc/sources/data-sources.json`:
  golden-тест `packages/shared/src/data/sources.golden.test.ts` сверяет код с пакетом источника.
- Релиз: версия поднимается в трёх `package.json` (корень, `shared`, `client`) — HUD берёт её
  из сборки; запись добавляется в [CHANGELOG.md](CHANGELOG.md) с датой и разделами «Добавлено» /
  «Исправлено».
- CI ([`.github/workflows/ci.yml`](.github/workflows/ci.yml)) повторяет то же на push и PR:
  `npm ci` → `npm run verify` → `npm run build` → проверка, что dev-панели нет в бандле.

## 7. Границы и чек-лист агента

**Всегда:** читать `doc/rules.md` до реализации механики; держать ядро изоморфным; отправлять наружу
только `SanitizedGameState`; добавлять тест к изменению; прогонять `npm run verify`.

**Спросить у владельца:** спорное прочтение правил; данные без подтверждения источником; новая
зависимость; любое отклонение от 1:1; удаление существующего теста или механики.

**Никогда:**

- оставлять заглушки, `// TODO` и нереализованные ветки без явной ошибки;
- писать `any`, `Math.random()` в правилах, `@ts-ignore` / `@ts-expect-error` ради обхода типа;
- мутировать состояние партии в клиенте или отдавать клиенту полный `GameState`;
- выдумывать составы колод, тексты карт, топологию поля и вероятности вместо сверки с оригиналом;
- добавлять правовые оговорки и дисклеймеры (§5);
- править `doc/rules.md` — это текст оригинала;
- переписывать историю git, force-push, менять `.gitignore` / `.prettierignore`, чтобы спрятать материалы;
- удалять падающий тест, чтобы «починить» прогон.

**Перед сдачей:**

- [ ] `npm run verify` зелёный, новые тесты покрывают изменение и негативный случай;
- [ ] логика сверена с `doc/rules.md`, источник чисел отражён в `doc/sources/data-sources.json`;
- [ ] механика, тексты и числа взяты из оригинала, а не заменены упрощением или «балансировкой»;
- [ ] в коде нет `any`, заглушек и `// TODO`;
- [ ] комментариев-пересказов не добавлено, имена объясняют код сами (§3.1);
- [ ] ни один затронутый файл не превысил 1000 строк; новые файлы — ≤500 (§3.2);
- [ ] в `packages/shared/` нет React, DOM, Node и сети;
- [ ] наружу уходит только `SanitizedGameState`: ни UI, ни будущие боты не видят скрытых полей;
- [ ] нет `Math.random()`, партия воспроизводится по мастер-сиду;
- [ ] стили — классами Tailwind, новых `.css` нет;
- [ ] правовых оговорок и дисклеймеров не добавлено;
- [ ] версия и CHANGELOG обновлены, если это релиз.
