## 3. Три дефекта, которые стоит закрыть раньше всего (P0)

### P0-1. Мешок Чужих не тасуется: порядок жетонов одинаков для любого сида и виден игроку

- `packages/shared/src/logic/setup.ts:336` кладёт в состояние `createIntruderBag(playerCount)`,
  а `setup.ts:102–107` строит массив в жёстком порядке и никогда его не перемешивает
  (`shuffle` в файле применяется только к комнатам, жетонам Исследования, капсулам и Координатам).
- Эксперимент: для сидов `seed-aaa` и `seed-bbb` при 4 игроках порядок мешка совпал
  (`blank larva-1 … larva-4 creeper-1 queen-1 adult-1 … adult-7`).
- `packages/shared/src/logic/sanitizer.ts` не трогает `intrudersPool.bag`, поэтому порядок виден
  в срезе состояния, который уходит в UI (и в будущем — ботам).

**Почему это важно:** Контакт на этапе 4 будет тянуть жетоны по одному и тому же сценарию
(сначала всегда Пустой и четыре Личинки, Королева — седьмой), а «скрытая» информация окажется
в клиентском состоянии. Это ломает и правила, и GDD §5.1.

**Что делать:** тасовать мешок потоком `bag` при подготовке; вырезать порядок из среза
(оставить только счётчики по типам); поднять `GAME_STATE_SCHEMA_VERSION`; тесты — «порядок
зависит от сида» и «в срезе нет порядка жетонов».

### P0-2. Первый запуск по LAN/HTTP падает целиком: `crypto.randomUUID`

- `packages/client/src/services/session/seed.ts:10` вызывает `crypto.randomUUID()`.
  Это API только безопасного контекста: на `http://192.168.x.x:5173` (телефон в той же Wi-Fi)
  и на любом http-хостинге `crypto.randomUUID` не определён.
- Эксперимент (vitest, `crypto` без `randomUUID`): `createSeed()` бросает
  `TypeError: crypto.randomUUID is not a function`, и **тот же TypeError вылетает из
  `createLocalTransport()`** — то есть на первой загрузке без сохранения.
- Вызов происходит при импорте модуля стора (`useGameStore` создаётся на уровне модуля),
  поэтому пользователь получает белый экран, а не сообщение об ошибке.

**Почему это важно:** это ровно тот сценарий («играть с телефона по локальной сети»),
ради которого в проекте `vite --host` и `allowedHosts: true`. Сейчас он не работает.

**Что делать:** генерировать UUIDv4 через `crypto.getRandomValues` (он доступен и в
небезопасном контексте), предпочитая `randomUUID`, когда он есть; добавить тест на fallback.

### P0-3. Вскрытие отсека исполняется наполовину — и это противоречит собственному принципу проекта

- `packages/shared/src/logic/fsm.ts:207` после перемещения ставит только `EXPLORE_ROOM_INTERRUPT`,
  а `fsm.ts:234–244` переворачивает тайл и на этом заканчивает. Броска кубика Шума нет вовсе.
- Эффект жетона Исследования (Огонь / Поломка / Слизь / Двери / Опасность / Тишина) не
  сохраняется даже в данных: `setup.ts` вытягивает из пула только `itemsCount`, а
  `ExplorationToken.effect` теряется; в `RoomState` (types/rooms.ts) поля под эффект нет.
- Правила при этом требуют: эффект жетона разыгрывается, «Тишина»/«Опасность» отменяют бросок
  Шума, иначе бросок обязателен (rules.md, стр. 14–15). Заметим: правила «Опасность» ещё и
  двигают Чужих из соседних отсеков, а «Двери» кладут жетон в коридор.

**Почему это важно:** движение в неисследованный отсек сейчас даёт игроку половину правила,
причём без ошибки. Это нарушает заявленный принцип из README: «Действие, которое ещё не
реализовано, отклоняется явной ошибкой, а не „ничем“». Кроме того, доделать механику без
изменения контракта состояния уже нельзя, а значит `GAME_STATE_SCHEMA_VERSION` придётся
поднимать в любом случае.

**Что делать:** хранить в `RoomState` выпавший жетон (или его эффект); реализовать
`NOISE_ROLL_INTERRUPT` (с учётом Слизи, Тишины и Опасности); до реализации — отклонять вход в
неисследованный отсек явной ошибкой `INTERRUPT_NOT_IMPLEMENTED`.

## 4. Достоверность данных: главный содержательный риск (P1)

Тесты в проекте — «регрессионный слепок»: они проверяют, что данные не изменились, а не что
они совпадают с оригиналом. Это честно записано в комментарии (`shipGraph.test.ts:158`:
«требуют сверки с физическим полем»), но означает, что ошибка в таблице пройдёт мимо тестов.

Конкретные несоответствия и неопределённости:

| Что                                     | Где                                                     | Проблема                                                                                   |
| --------------------------------------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| Пул жетонов Исследования                | `setup.ts:37–56`, `setup.test.ts:32`                     | 16 жетонов с суммой предметов 34, тогда как в списке компонентов правил — **20** жетонов (rules.md, стр. 3), а в коробке 4 из них остаются. Числа 16/34 не выводятся из книги правил |
| Числа Внезапной атаки взрослых особей   | `setup.ts:103`                                           | `[2,3,4,4,1,2,3,1]` — придуманы; комментарий сам просит сверки                               |
| Топология коридоров и вентиляции        | `shipGraph.ts`, `shipGraph.test.ts:158`                  | Источник (`corridor_table.md`, кропы 016/018/021) в репозиторий не попал — проверить нечем    |
| Компьютер у Мостика                     | `setup.ts:256`                                           | Назначен кодом (`node.id === 1`), а не взят из символа на тайле/поле                          |
| Номера Машинных отсеков                 | `shipGraph.ts:19–21`                                     | Соответствие «отсек 19 → Двигатель #03» и координаты нужно сверить с полем                    |
| Типы Чужих (Трутень, Яйца)              | `entities.ts` (`BREEDER` есть в типе)                    | Трутни в мешке не участвуют, но и в механике Развития Улья их пока нет — нужно решить, где они  |

**Что делать:** завести в репозитории «пакет источника» (сериализованные таблицы, фото/скан
жетонов и поля), рядом с каждой таблицей — запись о происхождении (страница правил, фото,
кто сверял, дата), и golden-тесты на числа из оригинала. Тогда «1:1» станет проверяемым
утверждением, а не лозунгом.

## 5. Что ещё доработать (P1–P2)

**Документы и процессы**

- README (`README.md:9, 60`) ссылается на несуществующий `doc/audit-0.1.0.md`, и на «аудит
  №22 / §4, P1-1 / §3.1» ссылаются комментарии в `App.tsx`, `env.ts`, `fsm.ts`, `setup.ts`,
  `sanitizer.ts`, `DevPanel.tsx` и др. Либо вернуть документ в репозиторий, либо заменить
  ссылки — сейчас это 10+ висячих указателей.
- `doc/tech_stack.md` описывает как существующее то, чего нет (`packages/server`,
  `SocketIoTransport`, `pathfinding.ts`, PWA, Howler, Framer Motion), а примеры кода
  противоречат фактическим типам (`topTokenWorking`, `secretObjective`, `undefined as any` —
  при этом сам проект запрещает `any`). `doc/design_document.md` называет Мостик «№2», хотя
  в данных он №1. Стоит разделить «сейчас»/«цель» и синхронизировать схему с `types/state.ts`.
- Нет CI и порогов покрытия (`vitest.config.mts` без `thresholds`): 100% ядра держится на
  дисциплине, а не на автоматике. Нет тегов, CHANGELOG и осмысленной истории (в репозитории
  один коммит `0.1.9 - improvements`, тегов нет) — откатиться к «той самой 0.1.9» нечем.
- `npm audit`: 5 уязвимостей (1 high — Vite, 4 moderate — vitest/@vitest/mocker/esbuild).
  Для dev-инструментов это терпимо, но обновление Vite (и, при готовности, vitest 5) стоит
  запланировать. Нет `engines`/`packageManager` при требовании Node 20+ в README.

**Модель правил**

- `nextDoorState` (`types/rooms.ts:15`) зациклен: «Разрушена → Открыта → Закрыта», но правила
  прямо говорят: «Разрушенные Двери **не могут быть снова закрыты**» (rules.md:1044).
  Заодно в модели нет запаса из 12 жетонов Дверей и правила «не хватает жетона — переставь
  существующий» (rules.md:1047).
- `rng.ts` обещает, что «счётчик обращений лежит в `GameState`» и поток восстанавливается из
  сохранения, но в `GameMeta` таких счётчиков нет. Пока это не мешает (потоки только читаются
  при подготовке), но обещание в комментарии опережает код.
- `ACTION_PASS`, `ACTION_SEARCH`, `ACTION_CLAIM` и прочие действия контракта отклоняются
  `ACTION_NOT_IMPLEMENTED` — это осознанная политика, вопросов нет; но `PlayerState`
  (`hasPassed`, `actionsPerformedThisRound`) и цикл микрораундов из GDD пока не тронуты,
  а режимы на 2–5 игроков недостижимы из UI: `createLocalTransport` всегда `player-1`,
  DevPanel не даёт выбрать число игроков. То есть README-овское «партия для 1–5 игроков»
  сегодня верно только для подготовки стола, а не для интерфейса.

**Клиент**

- Нет ни одного DOM-теста: клиентский vitest работает в `environment: 'node'`, `jsdom` и
  testing-library не подключены; покрытие `packages/client/src/components/**` — 0%.
  Проверяется только `devPanelModel`.
- Доступность: комнаты — это `<g onClick>` без `role`/`tabIndex` (карта недоступна с
  клавиатуры), кнопки зума подписаны только `title`, в `index.html` стоит
  `maximum-scale=1.0, user-scalable=no` (блокирует масштабирование слабовидящим),
  нет `eslint-plugin-jsx-a11y`; type-aware правила ESLint (`strictTypeChecked`) не включены.
- Дублирование данных: `CANONICAL_ROOM_NAMES` в `RoomHex.tsx` повторяет названия из
  `roomDefinitions.ts` — рано или поздно разойдётся; лучше брать название из определения.
- Офлайн и PWA: сервис-воркера нет, шрифты тянутся с Google Fonts, поэтому «сеть не
  требуется» верно только для уже открытой вкладки; холодный старт без сети и установка на
  телефон (этап 9) не работают. Стоит либо смягчить формулировку, либо локализовать шрифты.
- Мелочи: нет `ErrorBoundary` (любое исключение рендера — белый экран), `structuredClone` +
  `JSON.stringify` всего состояния на каждое действие (при 21 отсеке нормально, но запас
  заложить стоит), компоненты карты не мемоизированы.

## Приложение. Как воспроизвести проверки

```bash
npm ci
npm run verify            # типы + ESLint + Prettier + 228 тестов
npm run test:coverage     # ядро: 100% statements, 93.6% branches; компоненты клиента — 0%
npm run build             # 238 кБ JS (77 кБ gzip), 16 кБ CSS; dev-панель в бандл не попадает
npm audit                 # 5 уязвимостей: 1 high (Vite), 4 moderate (vitest/esbuild)
```

Эксперименты, подтверждающие P0 (временные тесты, после прогона удалены):

1. **Порядок мешка.** `createInitialGameState('seed-aaa', { playerCount: 4 })` и
   `createInitialGameState('seed-bbb', { playerCount: 4 })` дают одинаковый
   `intrudersPool.bag.map(t => t.id)`; `filterStateForPlayer(state, 'player-1')` отдаёт этот
   порядок наружу (`bag` в срезе не фильтруется).
2. **Сид в небезопасном контексте.** При `globalThis.crypto = { getRandomValues }` (как на
   `http://<LAN-IP>`) и `createSeed()`, и `createLocalTransport()` бросают
   `TypeError: crypto.randomUUID is not a function` — то есть падение происходит при импорте
   модуля стора, до первого рендера.
